## How to use this list

Work top to bottom: **P0 → P1 → P2 → P3**. Each item has the problem, where it lives, the fix, a
**Definition of Done (DoD)** checklist and the exact **retest** steps. An item is done only when every
box is ticked *and* Tegav's retest passes.

### Applies to every item (global DoD)

- [ ] Fix is on a branch with a PR referencing the item ID (e.g. `QA-01`).
- [ ] An automated test covers it where it's testable (unit in `packages/domain`, integration in `apps/api`, or Playwright E2E). Bugs get a test that **fails before** the fix and passes after.
- [ ] No test weakened, skipped or deleted; types not loosened (AGENTS.md golden rules).
- [ ] All new user-facing text goes through next-intl with **both bg and en** strings. No raw keys or enum codes on screen.
- [ ] Server-side rules stay server-side: never rely on the UI hiding something for security.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` green; the concurrency suite still shows exactly one CONFIRMED + one 409.
- [ ] Checked by hand in the browser at desktop width **and** 390px, in bg and en.
- [ ] Mark the row in `docs/qa/reports/<date>.md` as "fixed — awaiting retest".

## P0 — Fix first (broken core flow or data integrity)

### QA-01 · Dialog text fields lose focus after every keystroke
**Found in:** K12 (walk-in name saved as "Q"), A6 (restriction note "QA тест A6" saved as "Qтест"). Affects every modal with a text input.
**Cause:** `apps/web/src/components/Modal.tsx` has a `useEffect` that calls `dialogRef.current?.focus()` with `[open, onClose]` as dependencies. Callers pass an inline `onClose` (e.g. `ClubCalendar.tsx` → `onClose={() => setSelection(null)}`), so each keystroke re-renders the parent → new `onClose` → effect re-runs → focus jumps to the dialog container.
**Fix:** In `Modal.tsx`, store `onClose` in a ref (`const onCloseRef = useRef(onClose); onCloseRef.current = onClose;`) and make the focus/keydown effect depend on `[open]` only, using `onCloseRef.current()` for Esc. Focus the dialog only on the open transition.
**DoD:**
- [ ] Typing a full name in the calendar walk-in dialog keeps focus and saves the whole string.
- [ ] Same for: moderation restriction note, delete-confirm text, booking dialog, any other `<Modal>` with an input (grep all `<Modal` usages and check each).
- [ ] Esc still closes the modal; focus still moves into the modal when it opens and returns on close.
- [ ] Playwright test: open walk-in dialog, type "QA walk-in K12", submit, assert calendar entry shows the full name.
**Retest:** K12, A6 (restriction note), plus type into every modal you can find.

### QA-02 · Default city "София" finds no tennis clubs (duplicate city)
**Found in:** P4. Cities "София" (id 5) and "Sofia" (id 4) both exist; tennis clubs are under "Sofia".
**Cause:** City is free text when creating/editing a club; `clubs.service.ts` (lines ~349 and ~493) does `city.upsert({ where: { name: input.city } })`, so any spelling creates a new city. Also root cause of A4 concern.
**Fix:**
1. Data migration: merge "Sofia" into "София" (repoint `Club.cityId`, delete the duplicate). Make it idempotent and safe on prod data.
2. Club create/edit (platform admin form + club profile): replace the free-text city with a **select of existing cities** (+ a separate "add city" action for platform admin only).
3. ~~City slug / case-insensitive matching~~ — **deferred post-MVP (Ivaylo)**. Store an English display name per city so it shows in the user's language.
**DoD:**
- [ ] Only one Sofia city exists after migration; all 3 Sofia clubs belong to it.
- [ ] Home search with default location finds the tennis clubs (Ace, Baseline).
- [ ] Creating a club can no longer create a duplicate city by spelling.
- [ ] City shown in the user's language on club cards/pages.
- [ ] Migration has a test (or a dry-run script with output) proving no club loses its city.
**Retest:** P4 (София + TENNIS + today → results), A4 (create club → city chosen from list).

### QA-03 · Admin calendar shows closed days as free; lessons/group sessions not distinguishable
**Found in:** K11. Closure 21.10 shows every slot as "+" (free) in `/admin/clubs/:id/calendar`; public grid correctly shows "Недостъпен". Group session (17.10) and lessons look like ordinary court bookings.
**Cause:** Closures are stored as `ResourceException` rows (`clubs.service.ts → createClosure`); the calendar endpoint (`reservations.service.ts`, calendar query ~line 360) only reads reservations, not exceptions.
**Fix:**
1. Calendar API: include resource exceptions (closures) for the day, per court, with reason.
2. Calendar UI (`components/admin/ClubCalendar.tsx`): render closed cells as "Затворено — <reason>" (not clickable for booking); render LESSON with coach name, GROUP session with title + "x/y записани", BLOCK with reason.
3. Legend: add **Урок**, **Групова тренировка**, **Затворено** (keep Свободно / Резервирано / Задържано / Блокирано). Every colour on the calendar must appear in the legend.
**DoD:**
- [ ] A closed day/time shows as closed in the admin calendar with the reason; no "+" there.
- [ ] Walk-in/block cannot be started on a closed cell (UI) and the API refuses it (server) — see QA-04.
- [ ] Lesson cells show player + coach; group session cells show title and participants count.
- [ ] Legend lists every state used; colours meet contrast in light and dark.
**Retest:** K11 on 21.10 (closure), 13.10 (lesson), 17.10 (group session).

### QA-04 · Verify closures vs existing bookings and walk-ins on closed days (server)
**Found in:** code review during K9/K12. `createClosure` inserts `ResourceException` rows with `createMany` and **no check for existing reservations**; I couldn't confirm a walk-in on a closed day is refused.
**Fix:**
1. `createClosure`: if any active reservation (HOLD, PENDING_PAYMENT, CONFIRMED — incl. lessons and group sessions) overlaps the window, even partly, **refuse** with `422 policy_violation` `{ reason: 'closure_overlaps_bookings', reservationIds }` and write nothing. **Decided by Ivaylo (§12 "Closure over existing bookings"): no `cancelOverlapping` option in MVP.** Depends on **QA-23**.
2. Staff walk-in and block creation (`/clubs/:id/reservations`, `/clubs/:id/blocks`): refuse when the slot is inside a resource exception (`reason: 'club_closed'`).
**DoD:**
- [ ] Integration test: closure over a confirmed booking → 422 with the overlapping IDs, nothing written. Same for HOLD, PENDING_PAYMENT, a lesson, a group session, and a partial overlap (09–12 closure vs 11:00 booking).
- [ ] Admin UI lists the affected bookings (date, time, court, customer); after staff cancel them (100% refund, QA-23) the same closure succeeds.
- [ ] Integration test: walk-in and block inside a closure → refused.
- [ ] UI shows a clear message listing the affected bookings.
**Retest:** K9/K10 variants: close a day that has a booking; try a walk-in on a closed day.

### QA-05 · Timed closure across several days only covers the first day
**Found in:** code review during K8. `createClosure` computes `end` for timed closures from `input.fromDate`, not each day — "23–24.10, 09:00–12:00" becomes one window on 23.10 only.
**Fix:** For `allDay: false`, create one window **per day** from `fromDate` to `toDate` (startMin–endMin each day). For `allDay: true` keep the single continuous window. Closure list should show one row per closure as entered.
**DoD:**
- [ ] Unit/integration test: timed closure over 2 days → both days blocked 09–12, gaps outside.
- [ ] All-day multi-day closure still one continuous window (existing K8 behaviour).
- [ ] Deleting the closure removes all of its windows.
**Retest:** K8 with "Цял ден" unticked over 2 days.
