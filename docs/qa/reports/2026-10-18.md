## Verified OK

- **Loader state machine** (`GlobalLoader.tsx:43-60`): when busy turns idle and then busy again within 350 ms, the effect cleanup cancels the hide timer, and `busy && visible` keeps it up ✅. Minimum time on screen: shown at t, idle at t+10 → `wait = max(350, 450-10)` = 440 ms, so 450 ms total ✅. All timers are cleared in the effect cleanup, so unmount is safe ✅. Changes in the in-flight count (1→2→1) keep `busy` true, so the effect does not re-run and the show timer is not reset ✅. `pointerEvents` is `auto` only while `mutating > 0` (`:77`) ✅.
- **Shape of `['me']`**: all 17 `useQuery({ queryKey: ['me'] })` callers use `queryFn: getMe → Promise<{ user: Me }>`, which is the shape `Providers.tsx:29` seeds and `/api/auth/me` returns (`auth.controller.ts:114-119`) ✅. SiteNav (5 min `staleTime`) and the default-15 s callers (CoachHubClient, AccountClient, MyBookings…) do not refetch on mount for 15 s after hydration ✅. Dependent queries (`enabled: me.isSuccess`) can now start on first mount, so the waterfall is one step shorter ✅.
- **Hydration**: `initialSession` reaches the client component as a plain-JSON RSC prop, so the server and client `useState` initializers seed identical data and produce the same markup. With `null`, nothing is seeded on either side, which is the old behaviour ✅.
- **No cross-user leak found**: a new QueryClient is created per render tree inside `useState` (not at module level), so each SSR request gets its own cache ✅. `fetch(..., { cache: 'no-store' })` and `cookies()` make the route dynamic, and Next 15 sends `Cache-Control: private, no-cache, no-store` for dynamic HTML. `next.config.ts` and `vercel.json` add no cache headers, and no route exports `dynamic = 'force-static'` or `revalidate` (only `sitemap.ts`) ✅.
- **After login**: `LoginForm.tsx:31` / `RegisterForm.tsx:45` run `invalidateQueries(['me'])`, and SiteNav's active observer refetches. The seed is read only when the QueryClient is created, and a later root-layout re-render (`router.refresh()`) passes a new prop that is ignored. **No stale-session path on client navigation** ✅. Google OAuth ends in a full redirect, so SSR seeds fresh data ✅.
- **After logout** (`SiteNav.tsx:51`, `AccountClient.tsx:38`): `qc.clear()` → `router.replace('/')` + `router.refresh()` → SiteNav refetches `/me` → 401 → signed out ✅. When the variable is set, the API sends two `Set-Cookie` clears, host-only and `Domain=` (Express 4.22 `res.cookie` appends) ✅.
- **Bearer forwarding**: `JwtAuthGuard.extractToken` accepts `Authorization: Bearer` and prefers the cookie when both are present. The server-to-server call carries no cookie ✅. A cookie value with CR/LF makes `fetch` throw on the header, the error is caught, and the result is `null` ✅. On staging and prod, `API_BASE_URL` is https (`docs/DEPLOYMENT.md:85`) ✅.

## Findings

### M1: Major: a `Domain=.playslot.bg` session cookie reaches staging hosts (prod token exposure + cross-env collision) → **Tisho**
`apps/api/src/auth/auth.controller.ts:168-180`, `.env.example` (example value `.playslot.bg`), `docs/DEPLOYMENT.md:84-87` (staging = `staging.playslot.bg` / `api-staging.playslot.bg`).
- **Scenario:** prod sets `SESSION_COOKIE_DOMAIN=.playslot.bg` as suggested. A tester signs into `playslot.bg`, then opens `staging.playslot.bg`.
- **Expected:** the prod session stays on prod hosts, and staging uses its own session.
- **Actual:** the browser sends the prod JWT (`playslot_session`, `Domain=.playslot.bg`) to **every** `*.playslot.bg` host, including `staging.playslot.bg` (now read by its server through `session.server.ts` and forwarded) and `api-staging.playslot.bg`. Prod session tokens reach the staging servers, their logs and anyone with staging access. The cookie name is the same in both environments, so if staging also sets the domain, a staging login overwrites the prod cookie and the user is silently signed out of prod. If only one environment has a domain cookie, the two cookies are sent together, and `cookie-parser` keeps the first (older) one: on staging, the guard (`jwt-auth.guard.ts:69`) then tries the prod token and the tester appears signed out. If `JWT_SECRET` is the same in both environments, the staging token also works on prod. I could not check this.
- **Fix ideas:** a cookie name per environment (e.g. `playslot_session_stg`), or move staging off the prod parent domain (`*.staging.playslot.bg` with `Domain=.staging.playslot.bg`), and confirm the JWT secrets differ. Decide this before the variable is set anywhere.

### M2: Major: the blurred overlay now appears on every background refetch, including live SSE updates, and stays up for as long as a GET hangs → **Anton** (UX sign-off **Iveto**)
`apps/web/src/components/GlobalLoader.tsx:36-38, 70-85`. This regresses the rule the previous version kept on purpose: "a refetch over content that is already on screen never gets [the overlay]" (the old `coldFetching` predicate).
- **Scenario A:** a player has the club grid open (`AvailabilityGrid`) and another user books at the same club. The SSE `onmessage` handler runs `invalidateQueries(['availability', clubId])` (`AvailabilityGrid.tsx:98`; the same happens in `admin/ClubCalendar.tsx:99`), and the refetch takes more than 150 ms.
  **Expected:** the grid updates in place, with at most the thin bar. **Actual:** the whole page, including an open booking dialog (z 50 < overlay 200), blurs for at least 450 ms with "Зареждане…", with nothing done by the user. At a busy club this repeats on every booking. Screen readers announce "Loading" each time (a `role="status"` node is mounted and unmounted).
- **Scenario B:** any page whose cached query is older than the 15 s default `staleTime` refetches on mount (e.g. returning to `/me` after 20 s), and the content that is already on screen is blurred.
- **Scenario C:** a GET never settles (mobile network drop). `apiFetch` (`lib/api.ts:205-219`) has no timeout, so the page **stays blurred indefinitely**. It remains clickable, but it is unreadable. A hung mutation blocks all pointer input except the header indefinitely (this was already true before).
- **Fix ideas:** count only cold queries (`predicate: q => q.state.data === undefined`) plus mutations toward the overlay, and keep the bar for warm refetches. Add a client-side `AbortSignal.timeout` in `apiFetch`, or a max-visible cap.

### M3: Major (conditional): removing or changing `SESSION_COOKIE_DOMAIN` after rollout makes logout stop working and can mix two users' sessions → **Tisho**
`apps/api/src/auth/auth.controller.ts:184-188`.
- **Scenario:** the variable is set in prod and user A signs in (domain cookie). Later the variable is unset (rollback) or changed. A clicks "Изход" on a shared computer.
- **Expected:** A is signed out.
- **Actual:** `clearSession` clears only the host-only cookie, because it no longer knows the old domain. A's domain cookie (30-day TTL, `SESSION_TTL_SECONDS`) survives, and A **is still signed in** after a reload. If user B then signs in on that browser, the API sets a host-only cookie for B. The browser sends both, the older one (A's) first, `cookie-parser` keeps the first, and B is served **A's account**.
- **Fix ideas:** keep clearing every domain ever used (e.g. a `SESSION_COOKIE_LEGACY_DOMAINS` list), and/or revoke sessions server-side on logout. At minimum, add a "never unset once set" note to `docs/DEPLOYMENT.md`.

### m1: Minor: the SSR `/auth/me` call shares the global 120 req/min/IP throttle with every user → **Anton**
`apps/web/src/lib/session.server.ts:23-29`, `apps/api/src/app.module.ts:39-41`, `apps/api/src/main.ts:37`.
- **Scenario:** each signed-in hard load (full reload, `router.refresh()`) now adds one server-to-server request from the web server's egress IP (Vercel fra1). With `trust proxy 1`, every user's SSR call counts against **one** IP bucket, which the existing SSR reads (`getClubs`, `getCoach`…) already share.
- **Expected:** one user's load does not affect another's. **Actual:** above about 2 SSR requests/s site-wide, the guard returns 429. The session falls back to `null` (handled), but the same bucket is exhausted for the public SSR reads, which then render empty or `notFound`. This risk existed before the commit; the commit makes it worse.
- **Fix ideas:** `@SkipThrottle()` for authenticated `/auth/me`, keyed by user id, or a server-to-server shared secret that bypasses the IP limiter.

### m2: Minor: every signed-in hard load waits for the API before any HTML is sent; up to 1.5 s worst case; public pages lose static prerendering → **Anton**
`apps/web/src/app/[locale]/layout.tsx:93`, `session.server.ts:9`.
- The comment "Resolved alongside the messages, so it adds no extra wait of its own" is inaccurate. `getMessages()` is a local import of about 0 ms, while the session call is a network round trip plus two DB queries (the guard's `findUnique` and `auth.getMe`). The root layout has no Suspense boundary or `loading.tsx` above it, so **nothing streams until `/me` answers**. TTFB grows by roughly one Vercel→API round trip per signed-in reload, and by up to 1.5 s when the API is slow. Signed-out visitors (no cookie) return early and pay nothing.
- Reading `cookies()` in the root locale layout makes **every** `[locale]` route dynamic. `generateStaticParams` still builds without error, but `/bg`, `/en`, login, register, the docs pages and so on are rendered on every request instead of being served prerendered. I could not run `next build` to list the affected routes (no servers or builds allowed).
- **Fix ideas:** lower the timeout to about 300–500 ms and measure p95 of `/auth/me` from fra1. Consider skipping the call on public marketing pages.

### m3: Minor: a waterfall of short requests (< 150 ms each) never shows the loader → **Anton**
`GlobalLoader.tsx:44-51`.
- **Scenario:** session 80 ms → 5 ms gap → profile 120 ms → 5 ms gap → clubs 100 ms → 5 ms gap → availability 140 ms (≈ 455 ms of loading).
- **Expected** (per the commit message, "shows once after 150 ms of activity"): the loader shows at about 150 ms. **Actual:** each idle gap runs the cleanup and cancels the show timer, so the 150 ms count restarts for every request and the loader never appears while the content arrives in steps.
- **Fix idea:** when the app goes idle before the loader is visible, wait for the same short grace period before cancelling the pending show.

### m4: Minor: `SESSION_COOKIE_DOMAIN` is not validated against the API host → **Anton**
`packages/config/src/env.ts` (`SESSION_COOKIE_DOMAIN: optionalString`).
- **Scenario:** a typo or wrong-environment value, e.g. `.playslot.bg` on an API served from `*.up.railway.app`.
- **Expected:** startup fails loudly. **Actual:** the browser silently rejects the `Domain=` cookie, and login returns 200 but nobody stays signed in. The same response also clears the legacy host-only cookie.
- **Fix idea:** at boot, check that `new URL(API_BASE_URL).hostname` ends with the domain (leading dot stripped).

- No unit test covers the GlobalLoader timers (fake timers: idle→busy within 350 ms, min 450 ms, hung request, pointer-events while mutating).
